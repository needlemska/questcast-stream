# questcast-stream

Свой стример для Quest 3: **захват → AMF → UDP → шлем**, без SteamVR, без Virtual Desktop и без
облачных сервисов Meta. Репозиторий — рабочая площадка для этапа 1: сначала измерительный стенд,
потом собственный конвейер вместо связки scrcpy + ADB.

Готовый «плоский» кастинг с коррекцией линзы, авто-горизонтом и LAN-клиентом живёт отдельно:
[needlemska/quest3-cast](https://github.com/needlemska/quest3-cast).

## Что уже работает

| Часть | Состояние | Где |
|---|---|---|
| UDP-транспорт: пакеты ≤ 1200 Б, сборка кадров, статистика потерь | работает, проверен побайтово | `src/QuestCastStream.Cli` |
| Живой режим: `live-send` / `live-recv` через stdin/stdout, свой демультиплексор | работает, 890/893 кадра, 0 битых | `src/QuestCastStream.Cli/Live.cs` |
| Стенд сквозной задержки (часы на экране → кадр у получателя → OCR) | работает, выдаёт CSV + сводку | `bench/` |
| Сквозная цепь экран → AMF → наш UDP → hw-декод → PNG | работает под нагрузкой 1440×1440/60 | `bench/stream2stream.ps1` |

Главный вывод по транспорту: **сам транспорт не добавляет задержки** — возраст кадра на выходе
из приёмника (`send_us` в заголовке → момент выдачи в декодер) p50 **0.0 мс**, p95 **1.0 мс**.
Значит всё, что видно в сквозной цифре, живёт до отправителя: в захвате и энкодере.

## Быстрый старт

```powershell
# сборка CLI
dotnet build src\QuestCastStream.Cli -c Release

# транспорт: отправить готовый HEVC-поток на получателя
ffmpeg -re -i test.h265 -c copy -f hevc - | `
  src\QuestCastStream.Cli\bin\Release\net10.0\questcast-stream.exe send --stdin --to 127.0.0.1:5000

# транспорт: принять и записать обратно в поток
src\QuestCastStream.Cli\bin\Release\net10.0\questcast-stream.exe recv --port 5000 --out recv.h265

# стенд задержки (нужны ffmpeg с AMF, mpv не нужен, tesseract для OCR)
powershell -NoProfile -ExecutionPolicy Bypass -File bench\glass2glass.ps1 -Samples 20
```

## Первые числа

Транспорт (loopback, 720p60 HEVC, ~20 Мбит/с):

- 360 кадров за 6.007 с, 13 266 пакетов, 20.9 Мбит/с, **36.9 пакета на кадр**, накладные расходы
  протокола **2.24 %**;
- принятый поток **побайтово совпадает** с отправленным (sha256);
- при искусственных 2 % потерь **194 из 360 кадров** собираются не полностью — FEC ещё нет,
  это первая задача транспорта.

Стенд задержки (эталонный путь ffmpeg: `ddagrab → hevc_amf → mpegts/udp → ffmpeg`):

- p50 **583–608 мс**, разброс p95 ≈ 650 мс, стабильно, не растёт во времени;
- тот же энкодер на запись в файл укладывается в реальное время лишь на **0.956×** — то есть
  720p60 он еле тянет, а 1440p90 не потянет вообще;
- вывод: цифра описывает не «задержку кодека», а очередь, которую набирает ffmpeg-путь.
  Именно поэтому захват и транспорт пишем сами, а ffmpeg остаётся только как эталон.

Подробный разбор методики и ограничений — [docs/stage1.md](docs/stage1.md).

Стенд живого конвейера (`ddagrab → hevc_amf → наш UDP → hw-декод → PNG`, 1440×1440/60):

- 893 кадра отправлено, **890 принято, 0 битых**, 3 сброшено на переполнении очереди;
- пакетов 4156 в обе стороны, байты совпадают;
- возраст кадра в приёмнике p50 **0.0 мс**, p95 **1.0 мс**, max 160 мс (первый кадр);
- сквозная цифра по OCR держится около 0.58 с — ровно столько же, сколько даёт чисто
  ffmpeg-путь, и при этом приёмник получает кадр мгновенно. Отсюда вывод: **очередь сидит в
  ffmpeg (ddagrab + AMF), а не в нашем коде**, и её лечит только свой захват и свой энкодер.

Потолок энкодера на этой машине (Radeon 890M): **≈62 к/с при 1440×1440** (`hevc_amf`, `h264_amf`,
`av1_amf` — все в одном коридоре). То есть 1440p90 этот APU не отдаст ни в каком варианте, а
1440p60 — на пределе. Это аппаратное ограничение, его надо учитывать в целевых цифрах.

## Устройство репозитория

```
bench/          стенд задержки: часы, OCR, сценарий прогона
src/            C# CLI: транспорт (send/recv), сборка кадров, статистика
docs/           отчёты по этапам
results/        CSV и сводки замеров
```

## План этапа 1

1. **Транспорт** (готово): пакеты ≤ 1200 Б, seq/frame/flags, сборка кадров, статистика.
2. **FEC + NACK**: 10–20 % избыточности, чтобы 2 % потерь не ломали половину кадров.
3. **Захват** без CPU-копии: DXGI Desktop Duplication сразу в D3D11-текстуру.
4. **AMF напрямую**: HEVC 8/10 бит, слайсы, GOP, низкая задержка — через `amfrt64.dll`, без
   промежуточного `hwdownload`.
5. **Клиент в шлеме**: 2D-панель, jitter buffer 1–2 кадра, HUD с задержкой и потерями.
6. **Повторный замер** тем же стендом: цель — p50 ≤ 55 мс, p99 ≤ 90 мс на 1440p/90.

Каждый пункт закрывается цифрой из `results/`, а не «код написан».
